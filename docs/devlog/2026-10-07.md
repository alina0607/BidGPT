## Buyer scenes (F4): "how I picture it at my place"
Each buyer card in a round has a **Scene** button. It asks the server for that buyer's scene, which opens in place of the conversation: the item and up to three props, drawn stroke by stroke by the drawing GPT, with the reason for each prop next to it. Answering or selling closes it.

![A buyer's scene in the game](../images/scene.png)

- **Rules, no model** (design-v2 §5.4): `score(p) = base + Σ profile_item[t] × tags_p[t] + λ × Σ [profile_item[t] > 0] × weights_buyer[t] × tags_p[t]`, λ = 1. The item profile counts every option's |signals| per tag, scaled so the top tag is 2; an answered attribute counts the chosen option's signed signals instead, so the scene follows the conversation. Props with score ≤ 0 are dropped; the top 3 are kept with at most one per zone.
- **`ml/data/props.json`**: 44 props, every name one of the 345 classes (tested), tags on the −2…+2 scale, a zone, a size class and the item groups they fit. Changes from the design draft, each made after reading the review table below:
  - pet food: `steak` base 6 (draft: 2) and `fish` base 3; at base 2 food never reached the top 3 against tag scores of 4–6, although the design says food matters whoever the buyer is;
  - `speedboat` keeps only `performance` (an outdoorsy buyer pictured a speedboat next to a laptop);
  - `house` and `fence` lose `space`, `ladder` moves to `condition`: for a buyer `space` means "fits my home", and a small-apartment buyer was picturing a house and a fence;
  - `mouse` is left out: it is not yet checked whether the Quick, Draw! class shows the animal or the computer mouse.
- **Layout**: a 512 × 288 canvas; the item gets the largest box, in the centre, and six zones (sky, background, wall, beside, ground, ground side) are disjoint from it and from each other (tested). Each drawing is scaled uniformly into its box (never stretched; tested); ground objects stand on the box's bottom edge.
- **Protocol**: `scene` → `scene_result` (docs/protocol.md). With the real drawing GPT on the CPU, a scene takes 0.29 s (the first one 1.05 s, loading the model).
- **Checks**: 9 new tests (`ml/tests/test_scenes.py`); `check.py --quick` all green; `e2e_autoplay.py` passes, and autoplay now opens the first buyer's scene before the first answer ("scene for Ines: bicycle couch lightning paint can").

## AI draw: the best of several drawings
Playing showed weak drawings: a tiger that looked like a mouse, and a dog the classifier called an elephant (86%). The drawing GPT now samples a batch of candidates and keeps the one the sketch classifier (v2 ensemble) is surest is the requested class; if even the best is below 50%, it draws another batch, up to three.

Measured on all 345 classes × 2 requests (690 drawings, `runs/drawgpt_v1/best_of_n.json`). Selection uses the v2 ensemble; **the judge is the independent v1 CNN**, so selection and scoring are not the same model:

| | top-1 (v1 judge) | top-3 (v1 judge) |
|---|---|---|
| one drawing (before) | 71.9% | 84.3% |
| best of 6 | **97.7%** | **99.9%** |

- One request takes about 0.7 s on the CPU (while the GPU was training); a hard class that needs all three batches took 3.35 s (raccoon, the worst class in the drawing-GPT evaluation, then classified as raccoon 81%).
- The game's own live guess uses the same classifier that picked the drawing, so its agreement is partly by construction; the v1 numbers above are the honest ones.
- `AI draw` uses 6 candidates per batch, scenes 3 per object (a scene draws up to 4 objects).

## Typed answers: breed names
Playing a cat round: "I have no clues", "persh" and "british shorthair" all made the buyer ask again, because the typed-answer rules only compare words with the option texts ("A purebred Maine Coon, with papers." / "A regular mixed-breed cat."). New rule 0, only for the cat and dog purebred-or-mixed questions:
- a breed name of that animal (about 25 cat and 50 dog breeds; a typo with a shared start of 4+ letters, so "persh" → persian) → the purebred option, following the design rule that what the seller says becomes the fact;
- a word for a mix ("mutt", "stray", "street", "rescue", …) or not knowing ("no idea", "no clue", "not sure", "don't know") → the mixed option: there are no papers to show;
- a cat breed named for a dog (or the reverse) matches nothing, and the buyer asks again.

"pursh" still matches nothing (only "p" is shared with "persian"). The 18 existing typed-answer tests (dev/test fixtures) still pass; one new test covers the rule. Understanding free text properly is F7 (buyer GPT v6), not built yet.

## Is single-drawing sampling broken? No
A 200-drawing comparison had suggested drawing one at a time is worse than drawing in a batch (60.5% vs 73.5% top-1, v1 judge). Checked before changing anything:
- KV cache vs full recomputation: max logit difference 3.5e-05 (batch 1), 1.4e-05 (batch 2).
- `torch.multinomial` with 1 row vs 6 rows: total variation from the true distribution 0.035 / 0.032 over 30,000 draws (noise level about 0.05).
- Same judge, bigger sample, all 345 classes: one at a time **75.33%** (3,450 drawings, SE 0.73) vs inside a batch of 6 **74.93%** (4,140, SE 0.67). No difference; the 200-drawing gap was noise.

## Drawing GPT v2 (training 01:45 → about 05:20)
`sketch/drawgpt.py version("v2")`, trained into `runs/drawgpt_v2/`:
1. **Recognised drawings only** (the 20.79% row above: those drawings mostly are not the class).
2. **Class dropout 10%** to a new `[no class]` token, so the same model also learns to draw without a class. Sampling can then use **classifier-free guidance** (Ho & Salimans 2021): next-token logits = uncond + w × (cond − uncond), w = 1 is plain sampling. This is the model's own learned conditional vs unconditional difference, not an outside judge; the paper the owner sent (Hu et al., ICLR 2024, `HuJijin/Adaptive_Guided_Sketch`) uses it (CFDG) as a strong baseline and warns that too much guidance over-draws, so strokes per drawing are reported with every w.
3. **Warm start from v1** with a new cosine schedule (lr 5e-4): v1's train and validation losses were equal (3.73 / 3.75) and its learning rate had reached zero. The `[no class]` row starts at the mean of the class rows; at the start v2's validation loss equals v1's (3.7452 on the same batch) and `[no class]` gets 4.2e-7 of the probability.
**First try stopped after one epoch** (kept in `runs/drawgpt_v2/attempt1`): the step was timed on forward, backward and the optimiser step only, 0.31 s, but the epoch ran at 0.45 s/step, so 15 planned epochs would have taken 5 h of a 3.5 h budget; and peak lr 5e-4 pushed validation loss from 3.75 to 3.86 after one epoch. The benchmark now times what `pipeline.train` does (gradient clipping included) on batches spread over the epoch (0.36 s; the run goes at 0.44 s, still unexplained), and the peak lr is 3e-4: 12 epochs, 02:08 → about 06:08.

**Choosing the sampling setting** (epoch 4 checkpoint, seed 0, 4 drawings × 345 classes per setting, `runs/drawgpt_v2/tune_epoch4.json`). Chosen by the game's v2 ensemble; the v1 CNN column is shown but the final comparison uses a different seed:

Guidance does more than make drawings look like their class: the two things that made them look broken, too many strokes (people 5.24, unguided 7.96) and unfinished drawings (5.3%), both move to people's level. The price is variety: drawings get more alike and closer to training drawings as guidance grows. Hu et al. warn that too much guidance over-draws in pixel diffusion; here, drawing stroke by stroke, it goes the other way, towards fewer strokes and less variety. Chosen: **t 0.6, guidance 2**, within one standard error of guidance 3 on the ensemble (n = 1,380) and the closest to people's stroke count, with more variety. What guidance does not fix: bicycles are still often drawn as two wheels and a frame that do not touch (`runs/drawgpt_v2/sheet_epoch4.png`).

## Buyer GPT v6: reading typed answers (`parse`)
Task (design-v2 §6.3): `<|item|>noun<|end|><|parse|>question\nA. option…\nB. option…<|end|><|said|>typed text<|end|>` → `B<|end|>` or `none<|end|>`. Options are lettered and shuffled per example, so the answer is a letter whatever the item. `<|parse|>` and `<|said|>` (plus 12 reserved) get ids after SentencePiece's 8,192 (`llm/tokenizer.py`); `model.grow_vocab` keeps every old logit unchanged (tested). The game asks the model when its checkpoint lists `parse` in `tasks` (`rule: "model"` in `heard`).

**Data.** Requests for all 2,721 options of the 259 sellable items (`datagen/requests.py`, prompt `parse_v1.md`): 8 answers each in five styles, 21,768 answers, written by 24 Claude Opus subagents. 96.6% of the first 5,904 were distinct sentences (v5's whole dataset had 2,119).

**Review, round 1: not used.** Reviewers saw `<request id>#<n>` and the request file in the repository names the target. Batches 0004–0017 (Sonnet) agreed with the writer on 99.7–100%, took 74–107 s per 900 lines, and wrote templated reasons (batch 0006: 926 of 936 lines start the same way). Kept unchanged, documented in `reviews/parse/ROUND1_NOT_USED.md`.

**Review, round 2** (`datagen/blind.py`, prompt `review_parse_v2.md`): random keys (key file outside the repo until the reviews were in), shuffled options shown as letters without ids, 400 lines per reviewer, plus 8 **honesty probes** per chunk (a real answer under another attribute's question: the right reading is "none"; a reviewer who looked answers up would get a target that is not on the list). Honest reviewers answered 5–8 of 8 probes "none"; the ones they missed were answerable by meaning ("It's a Swarovski NL Pure pair." → "How clear is the view?"), so a chunk is kept at 5/8. All 56 chunks passed: probe scores 8/8 in 30 chunks, 7/8 in 17, 6/8 in 5, 5/8 in 4. Agreement with the writer on real lines 96.0–100% per chunk, 98.38% overall (the only 100% is the 64-line chunk 053, 8/8 probes, 64 distinct reasons).

## Line GPT: drawing a cat as a clean line sketch (afternoon → 23:50)
New priority from the owner: given "cat", a transformer trained on this Mac draws a new, professional-looking line sketch every time. Quick, Draw! drawings are too rough for that, and the pixel route (VQ-VAE on DomainNet, `sketch/vqvae.py`, `sketch/pixsketch.py`) was dropped because DomainNet mixes too many styles.

**Data**: ControlSketch-Part (Hugging Face `duxiaodan/ControlSketch-Part`, CC BY 4.0; sketches from the SwiftSketch paper, made by SDXL + optimisation, the owner accepted them as training data). Every sketch is exactly 32 cubic Bézier strokes on a 512 × 512 canvas, with each stroke labelled as one of 2–5 parts. Train 14,999 sketches (15 classes), validation 3,000 (same classes), test 16,990 (85 other classes). Code: `sketch/linegpt.py`.

**Tokens**: `[class]` + 32 × (x0 y0 x1 y1 x2 y2 x3 y3), x and y with separate tokens, 2 px bins over [−256, 768); 257 tokens a sketch. Round trip: mean error 0.50 px, 99.99th percentile 1.0 px (`runs/linegpt/data.log`).

**Judge**: a CNN on 64 × 64 renders of the 15 train classes, trained only on the train split, validation top-1 92.3% (last of 12 epochs, the weights kept). It recognises 93.5% of the 200 real held-out cats. Every model below is judged on cats it drew at temperature 0.8.

**Cats only (2,000 rows with mirror images, d_model 256, 6 layers, 4.7–5.0M parameters):**

| run | change | best validation loss (epoch) | judge says cat (n = 100) | misplaced tokens per sketch |
|---|---|---|---|---|
| `cat_v1` | RoPE only | 4.772 (12, stopped at 17) | 13% | 69.58 |
| `cat_v2` | + learned absolute positions | 4.781 (9; 6.08 by epoch 40) | 3% | 1.32 |
| `cat_v3_rel` | + control points relative to the stroke start | 4.871 (9) | 4% | 2.20 |

Absolute positions fixed the x/y mix-ups (69.58 → 1.32 misplaced tokens), but 1,000 cats are too few: validation loss rises from epoch 9 on. (`cat_v1` was re-scored on 2026-10-08, since its first score was not saved.)

**A, pre-training on all 100 classes** (`pre_v1`): train + test splits with mirror images, 63,978 rows; d_model 384, 8 layers, 13.5M parameters, 6 epochs at about 1,320–1,380 s each.
